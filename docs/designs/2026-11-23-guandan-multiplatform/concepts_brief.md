> 本简报的每一句来自两类来源：用户已明确说过的要求（标注为"用户原话"）与设计者推断（标注 `A#`）。凡属推断，都必须能在第 8 节找到编号。

## 1. 要解决的问题

一群想打掼蛋的人在 6 类终端上找不到一个"既能联机、又能离线陪 bot、还能把斗地主麻将加进来"的产品，导致每换一个平台或每加一个玩法，就要重做一遍牌桌与联机层，维护成本随平台数 × 玩法数相乘增长。

## 2. 目标

| # | 目标 | 对应成功判据 |
| --- | --- | --- |
| G1 | 六端（Windows / Linux / macOS / Android / iOS / Web+H5）都能完整打完一场掼蛋 | S1、S2 |
| G2 | 4 人联机对战可用，含断线重连与超时托管 | S3、S4 |
| G3 | 完全离线也能与 bot 打完一场（本地模式不依赖服务端） | S2 |
| G4 | 框架可扩展：新增玩法只写 RuleSet、不动框架核心；v1 以斗地主验证，麻将留到 v2 | S5 |
| G5 | 内测版先给自己人与种子用户玩，但按商业化上架标准做架构：账号、支付、风控、商店分发的接入点在内测阶段就已存在，后续上架不需要回头改战斗服与规则引擎 | S7 |
| G6 | 定位是**多玩法棋牌平台**而不只是掼蛋：运营在后台**不写代码**即可配置出一款新棋牌玩法并发布上线、可回滚，掼蛋是第一个玩法 | S12 |

## 3. 非目标

- 内测首版不启用充值、内购、皮肤商城（C1 已确认为商业化目标，但变现能力按 G5 只做"架构预留、内测不启用"；谁若在首版就要变现，这条必须重开）
- 不做赛事、赛季、战队、公会
- 不做 3D 牌桌、语音、直播
- 不做 AI 强化学习训练闭环（只保留数据接口与评估侧）
- 不做跨端账号体系之外的用户社交（好友、私聊）
- 不做观战之外的内容分发（短视频、攻略）

## 4. 约束

- **时间**：原定 18 周基线**已失效**（C7 要求零代码上新玩法，C8 选定通用规则 DSL，C9 定为"积木 + 源码"双视图）。新基线 **34～38 周（2 人全职）**，并设硬 gate：**第 16 周必须能用 Web 端 + 本地 bot 打完整场掼蛋（不含联机）**，联机内测推到 20～24 周，DSL 与编辑器在 M3–M5 完成。**版号已由 U5 决定暂缓申报**，首发只做 Web/H5 + 桌面自主分发，商店端与移动壳押后到申报启动之后。
- **人力**：1 名客户端 + 1 名服务端；0 名专职美术（`A3`）。
- **技术栈 / 平台**：引擎为 **Rust crate（唯一实现）**，双产物分发——客户端编译 wasm、服务端直接引用 native crate；服务端整体 Rust（HTTP/WS 网关 + 房间运行时 + 账号/支付/风控），具体框架在草案里定；客户端为**单套 Web 渲染**（Vue 3 + Vite + PixiJS 8）套三种壳：Tauri 2（Win/Linux/macOS）、Capacitor 6（Android/iOS）、浏览器直跑（Web/H5），因此客户端只需 wasm，不做原生绑定；PostgreSQL 16 + Redis 7；协议 protobuf。
- **语言边界**：不使用 Java（用户原话"尽量不用 java"）。若某环节必须引入第二语言，要在草案决策记录里单独立项，说明为什么 Rust 做不了。
- **合规 / 数据**：C1 已确认商业化上架，因此版号、备案、实名认证与防沉迷在商业化版本中是必需项（内测阶段以 TestFlight / 自有渠道分发，`A10`）；只采集对局必要数据（账号标识、对局日志、设备类型），不采集通讯录与位置。
- **第三方依赖**：短信服务商（国内可用云厂商短信，需模板报备，按 1～2 周计，`A5`）；支付与实名认证在商业化前接入，内测不启用。
- **运行环境**：仓库 `D:\java\git\guandan` 当前为空目录，无既有代码资产（`A7`）。部署地为中国大陆单区（U6），域名与 ICP 备案是 M0 前置项。

## 5. 成功判据

- **S1** 同一份 action log（seed + 配置 + 操作序列）在 Node 与浏览器分别重放，得到相同的 `stateHash`；CI 中该用例集 100% 通过。
- **S2** 六个产物（msi/dmg/AppImage/aab/ipa/静态站）均能在无网络环境下完成一局掼蛋：建桌 → 发牌 → 出牌 → 结算。
- **S3** 断网 5 秒后重连，客户端状态与服务端一致（`seq` 与 `stateHash` 校验通过），可继续出牌。
- **S4** 4 人真实联机连打 30 局，出现 0 次非法动作判定、0 次状态漂移。
- **S5** 新增斗地主时，`packages/core` 的改动不超过其总行数的 10%，且框架层单测全部通过。
- **S6** 1000 个并发房间压测：动作回执 P99 < 100ms，进程内存无持续增长。
- **S7** 内测版升级为商店版本时，账号扩展、支付、实名认证与防沉迷的接入只改 `apps/server` 与壳层，`crates/engine`、`crates/table-runtime` 零改动。
- **S8** 四条核心争议（同花顺与炸弹的序、逢人配能否组成同花顺、过 A 条件、抗贡条件）均可通过配置切换；同一套引擎在两种口径下各跑一遍回归用例，均无非法判定且用例全绿。
- **S9** 同一手机号账号分别在 Web 与桌面端登录，战绩与段位一致；对局中断线 10 分钟内重登可恢复到该局。
- **S12** 运营者不改代码、不发版，仅在后台即可完成"选玩法族 → 配规则 → dry-run → 灰度 → 全量 → 回滚"，配置出一款族内新玩法（例如跑得快），全程不重启服务、不更新客户端安装包。

## 6. 七镜头速记

| 镜头 | 追问 | 结论 |
| --- | --- | --- |
| 对立面 / YAGNI | 不做会怎样？有没有更小的做法？ | C1 定为商业化上架后，"只做 Web+H5 一端"与 P2P 两条最小路线都出局；仍可砍的是原生壳后置到 M2、变现在内测期只留接缝不实现，这两项保留为可砍的一半。 |
| 成本与配额 | 钱、额度、算力、人力谁付？ | 主要成本从 18 周变成 **32～36 周 × 2 人**，这是选择通用 DSL 的真实代价；服务端算力仍可忽略（`A4`、`A16`）；商业化目标另含版号代理、实名服务、客服与商店年费（`A9`）。钱不是瓶颈，人力与"语言设计能不能一次成型"是。 |
| UX 与开发者体验 | 谁要多学一步？谁要多等一秒？ | 玩家要多等一次服务端回执（乐观动画掩盖，<150ms 不可感知）；开发者的代价换成 Rust：增量编译秒级、全量编译与 wasm 优化构建是分钟级，六端产物的签名/打包链路要各学一遍；换来的是规则一份实现、死守确定性。 |
| 迁移与向后兼容 | 旧数据、旧调用方、旧配置怎么办？ | 新项目无旧数据迁移；真正的兼容问题是"规则配置变更后老回放放不出来"，因此规则配置与 `schemaVersion` 必须写进回放头。 |
| 可观测性与 SRE | 坏了怎么知道？怎么定位？怎么回滚？ | 没有值班团队，第一信号来自玩家反馈，因此"一键导出回放"必须在 M3 前具备；`stateHash` 不匹配计数是自动化可得的唯一强信号；**规则配置是第二个必须可回滚的东西**：每次发布带版本号、留审计、能一键退回上一版，否则出错只能靠重启猜。 |
| 长期技术债 | 半年后谁会为它付利息？ | 六笔：**自研规则语言本身**（要有语法文档、调试器、向后兼容策略，一旦发布就无法轻易改语法）、wasm/native 双产物一致性、六端壳签名与审核、支付对账与退款、AI 与人机混合房口径争议、后台配规则的"配置即炸弹"。第一笔是最大的一笔，它决定了这个项目更像"游戏平台"而不是"一款游戏"。 |
| 创造性催化剂 | 有没有被否得太早的第三种做法？ | 有：纯 Web + PWA + WebRTC P2P 联机，熟人房场景可完全省掉服务器。当时按"要排名/要回放/要防作弊"否决，但若 C1 结论是"小圈子自用"，这条路能省掉一半工程，应重新评估。 |

## 7. 已否决方案

| 方案 | 否决理由 | 什么条件下可能重新考虑 |
| --- | --- | --- |
| 全 Java 单语言（引擎用 GraalJS 跑 TS） | 本地单机模式需在手机端启动 JS 运行时，冷启动与包体不可接受 | 若放弃 G3（离线 bot 模式） |
| 双端各写一份规则引擎 | 掼蛋规则复杂，双实现必然漂移，产生"bot 打得通、线上判非法" | 不再考虑，这是本设计的核心约束 |
| Unity / Cocos 统一六端渲染 | 包体大、Web 端加载慢、2D 棋牌收益低、人力成本高 | 若 3D 牌桌从非目标变为目标 |
| 纯 P2P（WebRTC）无服务端 | C1 已确认为商业化上架：无服务端则无排名、无回放、无防作弊，且无法承载实名认证、防沉迷与运营数据 | 仅当商业化目标被明确放弃、项目退回熟人自用时重开 |
| 引擎用 Rust 但业务层仍用 Java（原 B 案变体） | 用户要求"尽量不用 Java"；引擎已是 Rust，业务再引入一套 JVM 运行时，等于同时维护两套构建、两套依赖与两类排障手段 | 若存在必须复用的既有 Java 服务或中间件硬依赖 |
| A 案：Java 业务 + Node 战斗 + TS 引擎 | 与 Rust 单 crate 策略冲突；移动/桌面原生端无法直接消费 TS 引擎 | 若 Rust 原型在 M0 验证失败，且六端全部退回 WebView |
| 六端各写一套原生客户端 | 人力是 1 客户端，六套 UI 等于把 18 周变成 6 倍；牌桌交互与动效要在六处重复维护 | 若某端（如 iOS）有必须原生的性能或合规诉求，只对该端单独立项 |

| --- | --- | --- | --- |
| A1 | 引擎与服务端统一 Rust 可实现且可维护（异步、FFI、wasm 构建链都由同一人掌握） | 若 Rust 侧的构建与调试成本超出 2 人负荷，回退方案是"引擎仍 Rust、服务端改 Node 跑 wasm"，或整体降级为 TS 引擎（放弃原生端直连） | M0 内做一次 Rust 服务端 ↔ wasm 客户端的端到端原型，记录编译时间与调试体验 |

| A6 | Web/H5 是首发验证端，桌面与移动壳可后置到 M2 | 若必须首日就出六端安装包，M1 需并行投入壳工程，周期 +2 周 | 由 C4 确认节奏 |
| A7 | 仓库为空，无既有代码与历史包袱 | 若已有原型代码，需重估技术选型与迁移成本 | 已查证：`D:\java\git\guandan` 为空目录 |
| A8 | 单场对局并发度低（4 连接/房间），无高频广播需求 | 若加入实时旁观大量并发，需引入房间级广播扇出优化 | 观战排 M3，压测时验证 |

| A10 | 内测可通过 TestFlight（iOS）、自有渠道/企业签名（Android）、桌面自主下载完成分发，无需商店审核 | 若 TestFlight 对大陆区游戏同样要求版号，移动端内测只能延后到获批，`C4` 的节奏要重排 | 核查 Apple 中国区 TestFlight 现行政策与近半年同类拒审案例 |
| A11 | 同一 crate 编出的 wasm 与 native 在相同输入下产生相同 `stateHash`（无浮点、无 HashMap 迭代顺序依赖、无未定义行为） | 若两端结果不一致，联机判定与本地 bot 会分叉，必须引入"确定性纪律"，严重时退回单一运行时（服务端也只跑 wasm） | CI 中跑同一批 action log 双产物比对（S1 的 Rust 版） |
| A12 | 移动端走 WebView 壳（Capacitor），引擎统一用 wasm，不需要原生绑定 | 已由 `C4` 消除：客户端选中"单套 Web 渲染 + 三壳"，因此不需要 uniffi/cbindgen 绑定层；若日后某端改原生，这条会重新生效 | 已决定（2026-11-23），实现时以 `C4` 结论为准 |
| A14 | **通用规则 DSL 能表达目标玩法的全部规则结构**（出牌族、摸打族、比大小族的牌型、轮转、结算、计分、特殊流程都由声明式配置描述） | 若表达不了（如麻将的鸣牌优先级仲裁、掼蛋的进贡链），只能降级为"模板化 + 参数"，工期回落 6～8 周但"零代码"上限降低 | M0 用斗地主做反向验证：只用 DSL 配置实现斗地主，写不出来即降级 |
| A15 | 团队能在 M0 内跨过 Rust 异步服务端这道门槛（此前项目以桌面壳与插件为主） | 若 M0 结束时房间并发与断线恢复的原型跑不通，基线工期整体顺延 3～4 周或缩范围 | M0 交付"1000 房间空转压测"与"断线恢复"两个原型，实测记录 |
| A16 | DSL 解释执行的开销可接受：单次动作解释 < 1ms，单核可承载 1000 房间 | 若解释开销太大，需要引入编译缓存（RuleSet 预编译为字节码/闭包），工期 +3～4 周，且热更新复杂度上升 | M0 基准测试：同一 RuleSet 在 wasm 与 native 下各跑 10 万次 legal_actions 与 apply，记录 P99 |
| A17 | 编辑器以结构化积木为主视图，源码模式只作为研发的高级视图，两者读写同一份 RuleSet（已由 C9 确认，工期 +2 周） | 若源码模式成为主要入口，语法错误会直接进生产，dry-run 拦不住语义级问题 | 已确认（C9，2026-11-23）；M0 出交互草图与"非法结构不可构造"的验证 |
