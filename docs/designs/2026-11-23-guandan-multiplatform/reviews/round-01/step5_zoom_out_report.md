## 结论先行

这份设计的技术主线是扎实的——"规则只有一份实现 + 双产物哈希可比 + 恢复靠确定性重放 + 配置发布四级闸门"，比多数棋牌项目的认真程度高。它会整体不成立的地方不在技术本身，而在两处结构性错配：

1. **最贵的那 16～18 周，是为一个不存在的人建的。** 零代码 RuleSet、双视图编辑器、四级校验、灰度发布链，全部指向"非研发的运营在后台自己上新玩法"（§4.5、§4.10、D6/D7/D9/D10），但团队是 2 人、无运营岗（§3.3 约束 5、§8.1 角色表）、也没有第二款玩法的上线计划（§2.2 麻将不做、§2.1 斗地主只是"验证 DSL 表达力"的载体）。
2. **34～38 周之后没有任何一条收款路径被写下来，而唯一的合规触发点被自己删掉了。** §2.2 把支付/内购/广告/房卡全部推迟，U5 把版号与商店端移出关键路径，于是"上架前启用实名与防沉迷"（§2.1）这个触发点在计划里永远不会到来。

技术上最脆弱的三处集中在同一条链上——**确定性可观测**：`stateHash` 在客户端按 §3.3 约束 3 根本算不出来（F5-10）；wasm 端 `catch_unwind` 不成立（F5-12）；1ms 性能预算既当判定又当自动回滚的输入（F5-11）。而这条链正是 §3.2 自己认定的"真正的瓶颈"。

## 一、Zoom out：五个层面的成立条件与脆弱点

### 1. 商业模式：它需要一条不依赖商店、也已经被写进技术约束的传播回路

**成立条件**

1. 首版必须有一条分发与留存回路。文档选的是 Web/H5 + 桌面自主分发（U5、D18），组局靠房间码（§2.2 末段"好友与私聊不做"）。也就是说：产品自己不带社交，传播必须发生在产品之外的容器里（分享链接落进群/微信），而这个容器既不在 §10.7 的六端清单里，也不在 §3.3 的任何一条技术约束里（F5-15）。
2. 项目方必须扛得住"内测上线 → 版号到手 → 可收款"之间的空档。A9 给的是 6～12 个月，§2.2 又把所有付费点推迟到"以后"；两个日期从未在文档里相遇，最早的现金流起点是一个没有写进任何里程碑的日期（F5-02）。
3. 掼蛋的付费点必须能在"不做房卡、不做金币、不做广告、不做内购"的前提下成立。§2.2 当前答案是"首版没有任何付费点"，对应 A4 的首年 DAU < 1 万，收入为零。

**脆弱点**

- 收入路径缺失：全文没有一句写"第几个月开始收钱、靠什么收"。R5 只把渠道损失记成"机会成本"、按季度回看，而回看没有输入数据。
- 传播路径与产品设计相反：掼蛋的现实形态是熟人局，§2.2 明确砍掉好友与私聊。房间码能替代"拉人"，但替代不了"人从哪来"。
- 内容供给不足：平台叙事依赖玩法数量，v1 只有两款，其中一款是测试载体（§2.1）。
- 持续支出全落在无收入期：短信（A5）、ICP 备案、开发者账号、macOS CI runner、90 天镜像存档（D14）、监控告警。

**一旦不成立**：34～38 周不是投资而是消耗；R5 的"每季度看一次渠道机会成本"实际会变成"每季度看一次要不要停"。

### 2. 平台定位：它同时是"一款掼蛋"和"一个棋牌平台"，却只有一个里程碑

**成立条件**

1. 文档得先回答主定位。§1.1 写"一个想长期运营的掼蛋产品"（单品），§12.2 第二次变更写"定位从单款游戏改为多玩法平台"（平台），此后全文按平台写（§5 整章、G4、§8.1 的运营角色）。
2. 平台的可信度来自"能上多少款玩法"，而 C7/C8 之后平台的卖点变成"非技术人员也能上新玩法"——这需要一个非技术人员存在。
3. 六端是平台的覆盖面叙事，但 U5 之后 v1 只有 Web + 桌面三平台（§2.1 移动壳"押后"），叙事与交付事实不一致（F5-01）。

**脆弱点**

- G1–G5 里平台指标（G1 六端、G4 多玩法）与产品指标（G3 离线可玩）并列，没有任何一条规定冲突时保谁。
- 缩范围顺序（R2"先砍麻将族 → 再砍原生壳 → 最后砍观战"）把玩法、壳、观战都列为可砍，唯独把 DSL/解释器/后台这条 +16～18 周的线留成不可砍；工期危机时优先保的是平台野心，砍的是产品的可玩性与分发通道（F5-03）。
- "不绑定地区或平台"（C2）是平台化承诺，但 §5.1 的 `guandan-classic` 片段只给出一条 `compare.ladder` 序列，四条配置化争议覆盖的是"比较顺序"，覆盖不了"某地是否存在某牌型/是否需要多一个阶段"这类结构性差异（`patterns` 是数组可删项，`lifecycle` 是固定序列不能加阶段）。

**一旦不成立**：若它其实是单品，§5、§8.1、D6/D7/D9/D10 全是过度设计，基线该回 18 周；若它其实是平台，v1 只有两款玩法、没有运营人员、没有跨玩法复用证据，平台前提是空的。

### 3. 团队规模：68～76 人周要盖住 12 条交付线

**成立条件**

1. 我按 §2.1 的粒度做了一次**下限估算**（每项都取"顺利且已有栈经验"的下限，这是我加的显式假设 A-估算，文档本身没有逐项工时表，因此只能用来核对量级，不能当承诺值）：

| 交付项 | 我的下限估算（人周） |
| --- | --- |
| 引擎原语库（§5.2 十类原语）+ 掼蛋 RuleSet 表达与验证 | 6 |
| RuleSet 契约 + ADT + L1–L4 校验器 + schema 导出（§5.1–5.4） | 5 |
| 后台编辑器（积木 + 源码双视图同构，D7）+ schema 表单 + 发布链 + 审计（§5.6、§8.8） | 6 |
| table-runtime（七态、断线、托管、回放、观战，§4.5、§6） | 4 |
| 平台服务（账号/短信/JWT/匹配/战绩/排行/大厅，§4.4 自估 4～6 周） | 5 |
| 客户端（Vue 3 + PixiJS 牌桌、大厅、结算、设置、回放播放器） | 8 |
| 桌面壳三平台 + 签名/公证（R9） | 2 |
| AI L0/L1 + 三档难度（§2.1、U4） | 3 |
| 斗地主完整可玩（§2.1 作为 DSL 表达力验证） | 3 |
| 测试体系（172 条黄金/种子用例 §10.3、双端一致性 §10.4、故障注入、性能基线、模糊） | 4 |
| 运维与合规（告警分级 §7.5、每日对账 §6.6、镜像存档 §9.3、ICP/备案/部署/监控） | 2 |
| **合计** | **48** |

这 48 人周是"零返工、零 bug、零评审、零文档"的下限。34～38 周 × 2 人 = 68～76 人周，理论余量 20～28 人周要吸收全部返工与联调——而 §12.2 记录的是"同一天内改过五次、基线变了两次"（F5-05）。

2. 两人互为备份但各自单点：R6 的固定 owner 是"一人引擎 + DSL，一人平台 + 客户端"，引擎/DSL 只有一人能推进（F5-06 亦同源）。
3. 无值班（§7.5 自述），但值班对象有：PG、Redis、短信、发布链、镜像仓库、每日对账、每月演练。

**脆弱点**：48 人周下限 vs 68～76 人周上限；12 条线 ÷ 2 人；编辑/发布权限分离落在同一人；六端冒烟每次发布人工跑（§10.7）且押后端跑不了（F5-13）。

**一旦不成立**：§2.4 的阶段边界与 16 周 gate 必须重排；R2 的缩范围顺序在按 F5-03 修正前也不能成立（它砍的东西不能解决工期问题）。

### 4. 合规：四个前提都没有落成可验收的事实

**成立条件**

1. "无版号 + 免费 + Web/H5 + 桌面自主分发"在国内是可运营形态。**不确定**：需要版号代办对"牌类/掼蛋"品类的可申报性、以及"无版号免费内测"的边界给出书面答复（见 §不确定项）。
2. 无实名认证、无防沉迷可以先公网开放。§2.1 现在的写法是"接口占位 + 开关，上架前接真实服务商"——触发点依赖"上架"。
3. 素材能闭环。`license.md` 的收录规则是"只收 CC0 或明确允许商用且无需署名"，而登记表与字体节均为"（待补）"，即 0 条。
4. 个人信息处理有告知与同意流程。§8.4 只写了"存什么、怎么脱敏"，没有写"怎么取得同意、隐私政策放哪、撤回怎么办"。

**脆弱点**

- 触发点消失：U5 把上架移出关键路径，"上架前启用"在计划里不再发生（F5-07）。
- 未成年人路径完全缺失：没有年龄门槛、没有监护人同意、没有时长限制，而 §8.4 的手机号哈希方案本身不含年龄信息。
- 牌类版号的品类风险没被评估，只当成"6～12 个月的流程"（A9）。
- 素材规则自我封闭（F5-08）：`license.md` 把"有署名要求"等同于不可用，但主流可商用中文字体（OFL 类）要求的是随分发保留版权声明与许可文本，不要求 UI 署名——按现规则字体节永远填不满，而 2 人团队没有自绘中文字体的能力。

**一旦不成立**：公网开放日 = 风险敞口开始日；§2.1 的"合规适配层占位"从一个技术预留变成一个没有启用日期的空壳。

### 5. 技术路线：七条成立条件，五条当前不成立

**成立条件**

1. 确定性要跨 `wasm32-unknown-unknown` / x86_64 / aarch64 成立。§3.3 约束 2 只列了四条禁令（`SystemTime::now`、`thread_rng`、文件/网络 IO、`HashMap` 迭代顺序）；参与判定的**浮点运算、std 超越函数、序列化字段顺序、等价元素排序**都没有被约束（F5-16）。
2. `stateHash` 在服务端、CI、客户端三处都能算出同一个值——与 §3.3 约束 3 冲突（F5-10）。
3. 恢复能从快照起步——§6.5 的快照只有 `zoneDigest`（F5-09）。
4. 解释器的失败模式在 wasm 与 native 一致——§8.6 的 `catch_unwind` 在 `wasm32-unknown-unknown` 上不成立（F5-12）。
5. 性能预算与正确性判定分离——§8.6 的 1ms 预算既判"非法"又喂给自动回滚（F5-11）。
6. 六端 WebView 分歧有验证点（F5-13），且真实分享容器在验证清单里（F5-15）。
7. 容量基线与业务量级自洽（F5-14）。

**脆弱点**：第 2、3、4、5 条同时不成立，且第 1 条有漏项；它们全部落在"确定性可观测"这一条链上——而这条链是 §3.2 自己认定的"真正的瓶颈"，也是这份设计唯一比同类项目做得更好的部分。

**一旦不成立**：§1.4 S10、§6.5、§7.2、§7.6、§10.4、§9.3、D1/D12/D15 同时失效；届时"重放恢复 + 状态漂移告警"这套卖点会退化为一组不可执行的句子。

## 二、三条替代路径（心智实验）

### 路径 A：单款优先——砍掉 RuleSet/解释器，回到"每玩法一个 crate + 参数配置文件"

**做法**：引擎恢复成编译期注册的 `GameDef`（即 §4.10 变更前的形态），规则差异用一份强类型参数表表达（`bombOrder` 等四条仍在）；后台只做"参数表单 + 版本发布"，不做积木/源码双视图。

**它解决了本文档的哪个弱点**：直接消掉 F5-04（最贵的投入没有使用者）、F5-05 的永久税（双视图同构随原语数线性增长）、F5-03（平台不再压过产品），并让 R1（DSL 表达力不够）、R4（语法返工）、R13（`window` 未验证）三条"高/中概率 × 高影响"风险整体消失。基线回到 18 周量级，M0 的 gate 从"斗地主能否只靠 RuleSet 跑通"变成"掼蛋能否打完一整场"——后者才是产品的真实前置。

**代价**：放弃零代码上新（等于要求把 C7/C8 重新判定）；第二款玩法上线需要研发介入（按 §2.1 给斗地主的量级，约 3 人周/款）；D7 作废、§5 整章与 §8.6 沙箱大幅缩水；若未来确认平台需求，解释器要从头设计——但那时已有一款真实玩法的经验，比现在凭空设计语法更可靠。

**判据**：若 6 个月内没有第二款玩法的上线计划、也没有非研发的规则作者，这条就是正解。

### 路径 B：传播驱动——首版是"一个链接就能开的掼蛋房间"，只做 Web/H5 + 分享容器，桌面壳延后

**做法**：v1 只交付 Web 客户端 + 分享容器（含微信内置浏览器），组局靠链接而非房间码；桌面壳与六端整体推到 v2。

**它解决了本文档的哪个弱点**：消掉 F5-01（G1 不可达）、F5-13（押后端的冒烟列无法执行）、F5-15（分享容器不在清单里），并把 R9（三平台签名/公证/渠道）与 §10.7 的人工冒烟成本（六列 → 一列）一起削掉。它让"分发"退化成"一个 URL"，与 U5 的"无商店"结论天然一致。

**代价**：暂时失去桌面自主分发——那是 U5 用来绕开商店的唯一通道；WebView 的音频/切后台/安全区差异提前暴露且必须在 v1 内解决，而不能像现在一样押后；改动等于修订 C4（Tauri 进 v1）；手机号账号在分享容器里的登录体验要额外设计（容器内一键登录的体验会明显超过短信验证码）。

**判据**：看新增用户来源分布。若 >70% 来自分享链接，桌面壳就不该排在 M2 之前，这个顺序应该整体倒过来。

### 路径 C：去掉客户端 wasm——客户端只渲染，离线只在桌面壳里由 native 引擎提供

**做法**：G3（完全离线与 bot 打完一场）只在 Tauri 桌面壳内满足，用本地 native 引擎；浏览器端明确不承诺离线。S10 从"wasm vs native 同哈希"改写为"同一 crate 在多个 native 构建目标上同哈希"。

**它解决了本文档的哪个弱点**：一次性消掉 F5-10（客户端算不出全量 `stateHash`）、F5-12（wasm 端 `catch_unwind` 不成立）、F5-11（客户端侧的 1ms 预算问题），并让 §10.4 的双端一致性测试从"每次提交 + 每晚全量"降级为"多目标 native 构建一致性"；wasm 包体预算（§10.5 的 <1.5MB / 2MB 说明线）作废；§8.5"wasm 可被反编译"这条论证也失去对象（本地判定只服务离线练习，不参与线上权威判定）。

**代价**：G3 在浏览器端不可达（关标签即无离线），六端里的"Web 端离线"承诺必须删掉；若将来要做 PWA 离线，wasm 还得补；S10 会失去"跨引擎宿主可比"的意义，回放复现只能依赖 §9.3 的镜像存档（而 §9.3 本来就要求了）。

**判据**：若"离线"的真实需求只是"没网也能练一局"，桌面壳 + native 已经满足；只有"浏览器内必须离线"这个需求成立时，wasm 双产物才配得上它带来的测试面。

## 三、最脆弱的三个假设

### 假设 1：C7/C8"零代码上新玩法"是真实需求，且会有人真的用（概率高 × 影响高）

依据：R1 自评表达力不够概率"高"、影响"高"；而支撑这条需求的运营角色在 2 人团队里不存在（§8.1 角色表 vs §3.3 约束 5），第二款玩法的上线计划也不存在（§2.2、§2.1）。

**一旦不成立，要重写的章节**：§4.10 全节；§5.1、§5.2、§5.3、§5.4、§5.6、§5.8（RuleSet 契约、原语表、ADT 类型约束、四级校验、发布 API、四张表）；§8.6 沙箱边界；§8.1 的编辑/发布分离；§9.1 五条版本线中的 `interpreter` 与 `ruleset` 两条；§10.3 的"规则变异 12 条"；R1/R4/R13；D6/D7/D9/D10。等价于把 §12.2 的第二、三次变更整段撤回，基线回 18 周。

### 假设 2：2 人 34～38 周能把 12 条交付线推到内测（A1）（概率高 × 影响高）
