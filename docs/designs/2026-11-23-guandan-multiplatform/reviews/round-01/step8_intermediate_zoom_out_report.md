## 收敛结论（三句）

1. 这份设计实际要交付的是**一台规则发布机**（规则即数据 + 四级校验 + 灰度回滚 + 双端确定性执行），掼蛋只是它的第一个用例；文档自称的目标是**一款六端掼蛋产品**——两者不是同一件事，而文档没有把这个位移说出来。
2. 六个目标里，只有 **G2（联机/重连/托管）**在契约层真的被解决了；G3、G4、G5 是部分解决，**G1 按原文没被解决**（v1 只剩四端），**G6 在文档里不存在**。
3. 时间与人力基线**不成立**：四个时间口径并存且互斥，M2 的 4～8 周窗口装不下文档自己给出的 7～10 周工作量，"1+1+1=4～6 周"这处加法本身算错。要让设计从"写完了"变成"能开工"，改动集中在三件事：定一条能复算的基线、把验收口径对齐 v1 真实范围、给外部前置项一张带日期的日历。

## 1. 这份设计真正要交付的东西（一句话）

> **一句话：它要交付的不是"掼蛋"，而是一条"规则可以当数据发布、且发布出去一定可回滚、两端算出来一定一致"的流水线，附带这条流水线的两个用例（掼蛋、斗地主）。**

判断依据不是目录结构，而是三处重心证据：

- **工期重心**：16 周的硬 gate 只要求"Web 端 + 本地 bot 打完一场"（§2.4），联机被推到 20～24 周（U1）；而最大的一笔工期增量是"引擎从插件改为解释器"+16 周（D6），其次是编辑器双视图 +2 周（D7）。也就是说，前 16 周里真正吃时间的是 DSL，不是掼蛋本身。
- **文档重心**：§4 选型、§5 契约（RuleSet + 原语 + 四级校验 + 发布 API）、§8 沙箱与发布权限、§9 五条版本线、§12 的 D6–D10，全都在讲"规则怎么被安全地发布出去"；牌桌交互、动效、素材被明确划出范围（§2.3）。
- **范围重心**：移动壳押后（U5）、支付不做（§2.2）、实名与防沉迷只做适配占位（§2.1）、麻将完全不碰（U2）——"六端"和"商店版"这两个词已经从 v1 的交付里退出了。

**它和文档自称的目标不是同一件事。** 文档的自我定位是"掼蛋多端游戏框架 · 设计草案"（标题）与 G1"六端都能完整打完一场掼蛋"（§1.3）；实际交付是"多玩法规则平台骨架 + 四端掼蛋 + 斗地主"。这个位移不是错误，问题在于**文档没有把它写出来**：§1.3 的目标表、§2.1 的交付表、§12.2 的五次变更留痕各说各话，读者按哪一张表理解"做完是什么"，会得到三个不同的答案。这是 F8-01 的根。

## 4. 如果只能改三件事，是哪三件

标准是"改完就能把设计拆成任务卡发给两个人"。按这个标准排序：

**第一件：定一条能复算的基线，并把 M2 与 gate 的窗口对齐。**
要交付的不是"34～38 周"这句话，而是"哪几块、各几周、相加等于几周、第 16 周必须交出哪几项"。现状是 §3.3 认 18 周、§12.2 认 34～38 周、U1 认 16+20～24 周、§4.3 还用 18 周做选型论证。基线不定，R2 的"第 16 周 gate 未过即触发缩范围"这条机制就没有判定对象；一旦第 16 周真的没过，两个人会争论"是 gate 太早还是范围太大"，而不是执行预案。**这是开工第一天就要落到纸上的东西，所以排第一。**

**第二件：把 G1–G5 的验收口径对齐 v1 的真实范围，并同步改动三张表。**
要改的是：§1.3 G1（六端→四端）、§1.2 前提表 C1/C4（跟随 U5 标注已修订）、§10.7 冒烟清单（拆成"v1 四端必跑"与"v2 移动端待启用"）、§3.4/§11.3 开发者账号（移到移动壳启动条件）。**理由不是文字洁癖**：一份"做完"无法签字的验收标准，会让内测交付期出现两种失败——要么为了凑六端去补两个移动壳（多出未列入基线的工期），要么六端冒烟被执行成空动作（本就没有余量的 2 人白跑七项×4 端的发布清单）。同类问题还有麻将口径（§2.2 vs §2.4，F8-04），一并在这件里清掉。

**第三件：给四类外部前置项排一张带日期的日历，并把第一周动作写死。**
四类：ICP 备案、短信签名与模板报备（含企业资质）、素材授权清单、开发者账号与桌面签名/公证。它们都不在 68～76 人周里，却全部是硬前置或阶段前置。现在的状态是：ICP 备案在两个位置互相矛盾；素材台账 0 条；短信资质是否具备未写；账号依赖还停在已被押后的阶段。**任何一个没启动，第 1～2 周就会停在项目外面**——这类阻塞是设计文档写得再好也无法自己消化的。

**为什么不是别的三件**（重要，避免选错优先级）：

- **不是 DSL 表达力（R1 / R4）**。它是已登记的风险，已有 gate（M0 第 4 周用斗地主反向验证）、已有缩范围顺序（先砍麻将族→再砍原生壳→再砍观战）。它属于执行期要被触发的问题，不是开工阻断。
- **不是离线版 RuleSet 来源（F8-10）**。这是唯一一处"目标被写进 gate、契约却缺一块"的功能缺口，但它在 M0 内可以闭合（加一条"离线包内置 RuleSet + 版本号写入回放头"的规定），不需要在开工前解决。
- **不是可观测性 / 告警 / 回放包细节**。§7 已经细到指标名与阈值，属于可以直接派工的部分。
- **不是第三方选型复核**。§4.2 的事实本轮未核（URL 未获批准），但从文档自身逻辑看，S1 自建的结论主要靠"引擎必须同进程"这一条，不依赖那 7 个 URL 的细节；真正动摇结论的是 §4.4 的加法错误（已并入第一件）。

三件事的共同点：**它们都不是"再写点内容"，而是"把已经写下的东西对齐成一个能被别人执行的版本"**。这正好是这个设计当前最缺的一层。
